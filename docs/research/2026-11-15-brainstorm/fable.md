# Brainstorm: the compiler and the code (Fable)

Scope: Oscar64's code for NetHack's idioms, which data really needs far pointers, and the smallest
`#ifdef C64` amendments. Every experiment below ran in Oscar64's emulator (`oscar64 -Os -n -ep`,
pin 73, under `ulimit -v 3000000`); the files are in
a scratch directory (not kept)
(`t1.c`–`t7.c`, and `cal/` for the real-code runs). Tags: **[M]** measured by me, **[S]** sourced,
**[I]** inferred.

## 1. Long list

1. **`levl` as a table of 80 column pointers** (`#ifdef C64` in `rm.h`, one `const` table, two `sizeof` sites). On the real `is_pool`/`is_lava` and `mfndpos` code: **2.0x and 1.33x** [M]. NetHack already does this for vision (`viz_array` is `char **`, `vision.h:10`) [S: port tree].
2. **Compiler: inline constant multiplies by canonical-signed-digit recoding.** Oscar64 inlines only odd factors 1, 3, 5, 7, 9, 25 and calls `mul16by8` for everything else [M: `NativeCodeGenerator.cpp` ~9930–10300, `t7.c`]. NetHack's strides 126 (=128−2), 42, 22/24, 55 all go to the runtime; 480, 160, 24 are inlined.
3. **Compiler: widen the byte-index multiply table.** It exists (`AllocateShortMulTable`) but only for ranges < 16 [M]. Allowing up to 256 entries at `-Os` turns `x*126` into `LDA tab,X` (≈14 cycles, 160 B table for 80 columns).
4. **Compiler: opt-in "subscripts are in bounds"** (`#pragma`): an index into a declared `[80][21]` array gets range 0..79, so `int`/`xchar` indices qualify for 2 and 3. Today `__assume(x < 80)` does **not** help [M: `t5.c`].
5. **`dist2`/`distmin` through a squares table** (`#ifdef C64`, 160 B): ≈1,640 → 97 cycles a call in my harness [M: `t3.c`]; 388 calls a turn [M: callgrind] → ≈0.2 s/turn saved. Identical values.
6. **Bit-exact `lrand48` in assembler.** Not implemented yet for the C64; a portable-C version costs ≈4,900 cycles + ≈650 for the 32-bit `%` [M: `t6.c`]; 36.4 `Rand()` calls a turn [M: callgrind] → **≈0.2 s/turn** unpriced in the brief's estimate.
7. **`rn2(const)` fast paths**: 1,100 of 1,366 `rn2` sites have a constant argument [M: grep]; a `u32 % const` can skip the general `divmod32`.
8. **`monsndx()` divides by 55** (`divs16`, pointer subtraction) [M: `t6.c`]; 52 calls a turn. Compiler: division by constant via reciprocal multiply; or store `mnum`.
9. **Typed far spaces with 16-bit virtual pointers** (deep dive): no 3-byte pointers, no struct growth, no save-format change.
10. **Far by declaration for index-accessed tables**: `objects[]` is reached by index at 597 sites and by pointer at 2 [M: grep]; the compiler knows the base statically and needs no far pointer type for it.
11. **Keep heap and `level` near**: 64% of a turn's far accesses are heap, 13.5% `level` [M: `docs/data/fardata-trace-runB`]; far becomes mons + vision + display ≈ 2,700 accesses a turn (≈57 ms).
12. **Translation reuse** as CSE of a `far_xlat` IC op within a block, with pages pinned until the block ends: the spike's 1.7x instead of 3x.
13. **Far allocator alignment**: pad `mons[]` records to 64 B (4 a page), heap slabs by size, so no object straddles a page and one translation serves all fields.
14. **Compiler-inserted copy at far-string → near `char *` conversion**, replacing 26 KB of hand-generated string trampolines.
15. **Whole-program provenance check**: a pass that lists every `genericptr_t`/`char *` cast touching a far type (617 casts, 60% in `sp_lev.c`, `region.c`, `save.c`, `restore.c`, `timeout.c` [M]).
16. **Overlay static frames** by call-graph interference (SDCC/Keil-style): the 11.5 KB of `BUFSZ` frames mostly belong to functions never live together [I].
17. **`isok()` as a macro under C64**: 649 calls a turn at ≈53 cycles of call overhead [M: cal WORK=3] ≈ 3% of a turn.
18. **`-O2` / `#pragma optimize(speed)` on hot code: not worth it** — −9% on `is_pool`, −1% on `mfndpos` [M: `cal/o2_*`].
19. **`long` flag words are already fine**: Oscar64 tests one byte (`AND #$04`) for `flag & ALLOW_U`, `mflags1 & M1_FLY` [M: `t4.c`]. No work needed.
20. **`signed char` loop variables against `int` bounds** compile to 16-bit compares every iteration [M: `t4.c t_xchar`]; a compiler range-narrowing of promoted `xchar` would help throughout `mfndpos`-style loops.

## 2. Top five

### 1. Kill the column multiply: source now, compiler next
*What.* `rm.h`: `#ifdef C64 extern struct rm_s * const levl_cols[COLNO]; #define levl levl_cols #else #define levl level.locations`; `decl.c` initialises the 160 B `const` table from `level.locations[0..79]` (generated by a macro); `save.c:508`/`restore.c:750` use `sizeof(level.locations)`. Only those two sites use `levl` without two subscripts [M: grep of 772 `levl[][]` sites].
*Gain.* Real code, same checksums: `is_pool+is_lava` 7.69M → 3.80M cycles, `mfndpos` 58.5M → 43.9M [M: `cal/base_*` vs `cal/tbl_*`]. A turn makes ≈1,450 `level` accesses [M: trace]; at 250–450 cycles each the multiply is 0.3–0.4 s of the 1.26 s [I]. The compiler follow-up (ideas 2–4) also covers `level.objects/monsters[x][y]` (stride 42, 89 direct sites + `m_at`/`OBJ_AT`), `objects[otyp]` (597 sites) and `mons[i]`.
*Cost/risk.* Source: an hour, host build unchanged. Compiler: CSD recoding is ~100 lines in `ShortMultiply`, the table threshold one constant; the in-bounds pragma is a range-analysis hook and the only part with semantic risk (out-of-bounds indices already read garbage today).
*Experiment.* Done for the source form; for the compiler, change the `< 16` to `< 256` and re-run `calibrate.py`.

### 2. Typed far spaces with 16-bit virtual pointers
*What.* Instead of 3-byte pointers everywhere, make **pointer types** far: `__far struct permonst` (and what it contains: `struct attack`, the `mname` strings) means every `struct permonst *` is a 16-bit *virtual* address into that type's own space, translated through a per-type 256-byte TLB exactly as the spike does (same six-instruction hit path, 21 cycles; the "bank" byte is implied by the type). `struct monst` keeps its size, `mtmp->data` stays 2 bytes, `ptr - mons` and `ptr == &mons[PM_X]` stay valid, and `restore.c:264` already rebuilds `mtmp->data = mons + offset` so nothing persists a virtual address [M].
*Why it is cheaper.* 3-byte pointers grow `struct monst`/`struct obj` by 6–8 bytes each and the two pointer grids from 6.7 to 10 KB, change every save record, and touch every pointer operation in the compiler; typed 16-bit far pointers touch only load/store/lea through qualified types, a precedent being `__striped`, which already makes pointers to a struct type dereference differently [M: `Declaration.h` `DTF_STRIPED`].
*Provenance by type* [M: counts over `port/src`]: `struct obj_s *` 1,617 uses, `struct monst_s *` 1,060, `struct trap_s *` 152 → heap, **near**; `struct rm_s *` 71 → `level.locations`, **near**; `struct permonst *` 203 (+159 `->data->`) → `mons[]` only (`youmonst.data` is always `&mons[..]` or another monster's `data`) → **far**; `struct objclass *` 2 → `objects[]` by index → far by declaration (idea 10). Mixed types: `struct attack *` (mons or a local copy) and `char *` (literals, buffers, names) need a discriminator bit or a copy at conversion.
*Gain.* The spike's 1.7x on far loops applies only to the ≈2,700 far accesses a turn that remain once heap and level are near: ≈60–80 ms a turn instead of 0.25–0.5 s [I from the trace].
*Risk.* `genericptr_t` escapes (idea 15 is the guard); page eviction between two uses of one translation (idea 12).
*Experiment.* Hand-translate `mons[]` in the spike (`fardata.c`) with a 16-bit virtual pointer and a per-type TLB; then prototype `__far` on one struct type in the pin and compile `mondata.c`.

### 3. Place data by access count, not by size
*What.* The trace already ranks it: heap 6,893, mons 1,643, level 1,448, vision 943, display 79, globals 57 (after 4 KB near) far accesses a turn [M]. Near set: level 16.8 KB, heap 10–15 KB, hot globals 4 KB, stack 5 KB ≈ 36–41 KB; far: mons, objects, other tables, strings, vision/display (13 KB, mostly touched in `vision_recalc`, 0.26 calls a turn).
*Gain.* ≈75% of far translations gone before any compiler cleverness. *Cost.* The near set only fits with the KERNAL banked out (44 KB) and resident code near 15 KB; frame overlay (idea 16) buys back most of 11.5 KB [I]. *Experiment.* Re-run `summary.py` with heap and level marked near; check the fault counts of a 64-page cache on the rest.

### 4. The RNG, bit-exact, in assembler
*What.* `Rand()` is contractually `lrand48()` (c64conf.h) and is not implemented for the C64 yet. 36 calls a turn [M]. In C with 16-bit limbs: ≈4,900 cycles each plus ≈650 for `% x` [M: `t6.c`] ≈ 0.2 s/turn, missing from the 1.8 s estimate. A 48-bit LCG needs ≈21 byte products that matter (low 48 bits of a 48×35 product); with a quarter-squares table multiply (~30 cycles each) ≈1,000 cycles, plus a 32/16 remainder ≈400 → ≈50 ms/turn [I]. `rn2(const)` sites (80%) can use constant-divisor code.
*Risk.* Must match glibc bit for bit (seed handling, the `>> 17`); the host replay test catches any slip. *Experiment.* Write it, compare 10⁶ outputs against glibc in the emulator.

### 5. `dist2` squares table (+ `monsndx`, `isok`)
*What.* `#ifdef C64` in `hacklib.c`: `sq[abs(dx)] + sq[abs(dy)]` with an 80-entry `unsigned` table; `distmin` is already compare-only. 509 → ≈100 cycles [M: calibration vs `t3.c`], 388 calls a turn → ≈0.15–0.2 s. `monsndx`: 52 calls × a 16-bit divide (≈26 ms) → compiler reciprocal multiply or a C64 `mnum` field; `isok` as a macro saves ≈3%. All compute identical values; no ADR needed.

## 3. Deep dive: compiler and code

### 3a. Which data really needs far pointers
The compiler can know three things: the **static type** of every dereference, the **declaration** of every array indexed directly, and (whole-program) the **set of casts** that launder a pointer through `genericptr_t`/`char *`.

| Data | How it is reached | Mechanism | Pointer size |
|---|---|---|---|
| `mons[]` (21 KB, const), its `mattk`, `mname` | `struct permonst *` (203 decls, 159 `->data->`), `mons[i]` (733, mostly `&mons[PM_X]` constants) | typed far space, per-type TLB | 16-bit virtual |
| `objects[]` (11 KB, 2 KB mutable) | `objects[otyp]` 597 sites, pointer 2 | far by declaration: base known, offset `otyp*24` computed, one translation; writes go through the cache's dirty bit | none |
| `obj_descr`, `artilist`, `roles`, options (22 KB) | by index | far by declaration | none |
| strings (37.7 KB) | `const char *` to literals, buffers, heap names | copy at conversion (today's trampolines, moved into the compiler), or a virtual range with a high-bit test | 16-bit |
| `level` (16.8 KB), heap (10–15 KB), hot globals (4 KB) | `levl[x][y]`, `struct obj_s *`, `struct monst_s *` | **near** | 16-bit |
| vision/display (13 KB) | `viz_array[y][x]` row pointers, `gbuf[y][x]` in `display.c` | far with row pointers into the cache, or near if RAM allows | 16-bit |

So "far pointers" in the 3-byte sense are needed **nowhere**: each far type's space is under 64 KB, and the type says which space. The hard residue is `char *` (mixed provenance, byte loops) and `genericptr_t` (617 casts, concentrated in five files). `bwrite`/`mread` of whole structs are fine as long as no far pointer value is stored in a struct that is saved; `mtmp->data` is rebuilt on restore [M: `restore.c:264`].

What the compiler should do with a far type: (1) `IC_LOAD/IC_STORE` with a far-typed address operand go through `far_xlat` (in place, pointer in zero page, 19–21 cycles, as the spike); (2) `far_xlat` is a pure IC op, so existing CSE reuses it for the next field of the same object within a block, with the fault handler forbidden to evict pages translated in the current block (a pin count or epoch); (3) `IC_LEA` on a far base yields a far-typed pointer; (4) a far→near conversion of `const char *` materialises a copy into a rotating buffer; (5) any other far→near or near→far conversion is an error, which is the provenance check. Translation cost then falls on ≈2,700 accesses a turn, mostly `mons[]` fields in monster movement.

### 3c. Smallest C64 amendments that pay
1. `rm.h`/`decl.c`/`save.c`/`restore.c`: `levl` column table (≈15 lines, measured 1.33–2x on the hottest code).
2. `hacklib.c`: `dist2` via squares (≈10 lines + table).
3. `rnd.c`/`hal`: `lrand48` and `RND` in assembler, bit-exact (the RNG ADR is pending anyway).
4. `hack.h`: `isok` as a macro under C64 (identical semantics; `isok` is pure).
5. `mondata.c`: `monsndx` without division (store the index, or `(ptr - mons)` through a compiler constant-divide).
Everything else belongs in the compiler, because it covers hundreds of sites at once and keeps `port/` as NetHack.

## 4. Wrong, doubtful or missing in the brief

- **The 1.8 s/turn estimate omits the RNG**: `lrand48` is libc on the host (`__drand48_iterate` 728 Ir/turn) and unimplemented on the C64; in C it would be ≈0.2 s/turn, ≈50 ms in assembler [M/I].
- **"3-byte pointers"** is the expensive form of far data; typed 16-bit virtual pointers give the same hit path without growing structs, grids or save records, and the type counts above show every far type fits a 16-bit space [M/I].
- **The heap is the far-data lever**, not the constant tables: 64% of far accesses after 4 KB of near globals [M: run B]. The brief frames the problem as `mons`/`objects`/`level` not fitting; the speed problem is the heap being far.
- **`__assume` and `-O2` are not levers** for the two hot spots [M]; the brief implies "attention to speed" might come from optimisation levels.
- **Static frames are not overlaid** by Oscar64 as far as I can tell (each non-recursive function owns its frame) [I — verify in `Linker`/`InterCode` frame allocation]; if so, 11.5 KB is reclaimable without touching the game.
- The "250 cycles per `levl` access" is on the low side: `mul16by8` for 126 averaged 370–460 cycles in my microbenchmarks [M: `t1.c`, `t2.c`]; the gain is correspondingly larger.
- Missing hot items in the measured 12%: `isok` call overhead (649 calls), `monsndx` division (52), `t_at` list walks (90), `sobj_at` (42) [M: callgrind call counts].

Sources: Oscar64 README, https://github.com/drmortalwombat/oscar64 (no far-pointer or banked-data feature is documented; `__striped`, `__bankof`, `#pragma region` are the existing hooks); glibc `lrand48` = 48-bit LCG `a=0x5DEECE66D, c=0xB`, result `X>>17`, https://www.gnu.org/software/libc/manual/html_node/SVID-Random.html.
